## Уже принятые решения (оценить)

### Решение 1. Развязка multi-user: `owner_id` на каждой таблице
Не отдельная workspace-таблица. Для ≤10 пользователей это проще и дешевле в поддержке. Оцени, верно ли это решение, и при каких условиях стоит перейти на workspace.

### Решение 2. Внедрение скоупа owner_id — через конструктор BaseRepository

```python
class BaseRepository(Generic[T]):
    def __init__(self, model, session, owner_id: int | None = None):
        self.owner_id = owner_id

    async def get_by_id(self, id):
        q = select(self.model).where(self.model.id == id)
        if self.owner_id is not None:
            q = q.where(self.model.owner_id == self.owner_id)
        ...
```

Цепочка: роутер (`Depends(get_current_user)`) → сервис (`owner_id`) → репозиторий (`__init__`).

**Обоснование отказа от альтернатив:**
- **Per-call** (`get_by_id(id, owner_id=...)`): легко забыть аргумент → утечка данных между пользователями.
- **ContextVar**: теряется контекст в async-фоновых задачах (PollService, фоновые таски).

Оцени это решение. Наследники `BaseRepository`, строящие собственный `select()`, должны не забыть фильтр — как это гарантировать?

### Решение 4. Справочники (категории/шаблоны/сценарии) — всё per-owner

**Вопрос:** как обращаться с категориями/шаблонами/сценариями при multi-user — общие + клон на вход или всё per owner?

**Принятый вариант: всё per-owner.**
- Дефолты сидятся при создании workspace (не глобально).
- `slug` (глобальный UNIQUE сейчас) → составной уникальный индекс `(owner_id, slug)`, иначе два пользователя не смогут иметь одинаковый «default».
- Seed-версионирование: поле `seed_version`, чтобы новые дефолты в будущих релизах не трогали отредактированные пользователем.

**Проверь этот выбор.** Альтернатива (общие системные + клон на вход) — сложный copy-on-write и двухуровневый офлайн-кеш, не подходит под простоту. Но подтверди или опровергни.
