**Проблема.** `crypto.py:13-31` **[V]**: `:20` `if len(raw) == 44: return raw` — magic number; `:22-24` фолбэк на `_KEY_FILE`; `:26-30` генерация нового ключа и запись в файл. Если файл потерян — переустановка, чистка `data/`, перенос на другую машину без него — при следующем старте генерируется новый ключ, и все ранее зашифрованные `channels.config` и `ONBOARDING_FILE` становятся нерасшифровываемыми. **Важно:** предложение этапа 2 P1 #6 «сменить предупреждение на `raise RuntimeError`» нельзя брать буквально — оно сломает и первый запуск, и все существующие установки, живущие на сгенерированном файле; файл существует локально **[V]**. Нужен условный отказ.

**Что сделать.**

1. Заменить `len(raw) == 44` на явную валидацию: попытка `Fernet(raw)` в `try/except` — понятная ошибка при неверном формате вместо тихого перехода к фолбэку.
2. Ввести маркер «в системе есть зашифрованные данные»: существование `ONBOARDING_FILE` либо непустой `channels.config`.
3. Логика старта:
   - валидный ключ в env — использовать;
   - иначе файл существует — использовать;
   - иначе зашифрованных данных нет — сгенерировать; это первый запуск, текущее поведение;

5. Задокументировать критичность `.encryption_key` для бэкапа: `docs/` и `.env.example`.
6. Переопределить `__repr__` и `__str__` у `Settings` с маскировкой `SECRET_KEY`, `ENCRYPTION_KEY`, `TELEGRAM_API_HASH`, `TELEGRAM_PROXY_PASSWORD`, `TELEGRAM_PROXY_SECRET` (этап 2 §6).

**Файлы.** `backend/app/utils/crypto.py`, `backend/app/config.py`, `.env.example`, `docs/`.

**AC.**

1. Первый запуск на чистой системе — ключ генерируется, приложение стартует; текущее поведение сохранено.

**Тесты.** `tests/test_crypto.py`: четыре ветви выбора ключа; негативные — данные без ключа, невалидный формат; `test_config.py` — маскировка в `repr`.
